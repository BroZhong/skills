# Tech Read

## 目标

帮助读者真正理解一个技术领域、概念、实现或思想，而不是只给摘要。阅读过程要同时完成三件事：看清原文结构，讲透技术本身，激发读者形成自己的问题和判断。

最终效果应该是：读者知道作者在回答什么问题、为什么这个技术会出现、它到底是什么、内部如何工作、和哪些技术同构或相邻、能用在哪里、还能迁移到哪些问题上。

## 可接受输入

接受三类输入：

- 链接：打开并阅读原文。若页面无法访问，要求用户粘贴正文或提供替代来源。
- 本地文件：直接读取文件。若是 PDF、Word、PPT、表格等格式，使用当前环境中合适的文档工具提取内容。
- 项目目录：先读项目结构和入口资料，再建立阅读路径，不要一次性扫完整个项目。

分析项目目录时，按这个顺序进入：

1. 文件树、README、docs、架构说明。
2. 包管理、构建、运行和配置文件。
3. 入口文件、核心模块、关键抽象。
4. tests、examples、fixtures 或 demo，用它们理解预期行为。
5. 再深入实现细节、边界条件和设计取舍。

## 工作流

### 1. 建立阅读契约

先简短说明已经拿到什么材料、材料大概是什么类型。只有在来源不明确、范围过大或无法访问时才追问用户。

如果用户没有指定阅读节奏，默认使用 `normal`：

- `fast`：快速抓住核心观点、关键概念和结论。
- `normal`：按章节伴读，保留必要解释和检查点。
- `deep`：深挖概念史、机制、实现、类比、迁移和延伸阅读。

如果用户已经给出链接、文件或项目并要求开始，直接开始分析；不要为了节奏选择而停住。

### 2. 先画出原文地图

正式解释前，先给一张紧凑的阅读地图：

- 作者的核心观点或技术命题是什么。
- 这篇内容试图回应什么问题、痛点或争论。
- 文章/项目的结构是什么，每一部分承担什么功能。
- 作者的论证路径如何推进：从哪个问题走向哪个答案。
- 关键概念、API、算法、架构组件、设计选择有哪些。
- 哪些地方默认读者已经懂了前置知识。

然后提出 3-7 个导读问题。问题要帮助读者带着警觉进入文本，而不是做考题。优先使用这类问题：

- 为什么这里需要引入这个抽象？
- 作者真正想化解的取舍是什么？
- 哪一部分是机制，哪一部分是策略？
- 如果移除这个设计，系统会在哪里坏掉？
- 这个技术解决的是复杂性问题、性能问题、协作问题，还是表达问题？

### 3. 用五个镜头讲技术

遇到重要概念、技术或设计选择时，用 `why / what / how / relation / application` 五个镜头讲清楚：

- `why`：为什么提出这个概念？它回应了什么痛点、限制、历史压力或设计矛盾？
- `what`：它到底是什么？要区分名称、接口、行为、约束和保证，不要只给模糊比喻。
- `how`：它如何工作？必要时用步骤、伪代码、真实代码、数据流或调用链解释机制。
- `relation`：理解它需要哪些前置概念？它和哪些技术相邻、相似、容易混淆？有没有设计原理相同的技术？
- `application`：它适合解决什么问题？典型使用场景是什么？失效边界在哪里？它背后的思想还能迁移到哪里？

当代码能让机制变清楚时，给最小可用示例。编程主题优先用接近真实代码的例子；算法、系统设计或架构主题可以用伪代码。

### 4. 不清楚就补充检索

如果某个概念、历史说法、API 行为、最佳实践或版本信息不清晰，并且可能影响理解，要使用 web search 补充资料。

资料优先级：

- API、工具、标准、语言、框架：优先官方文档。
- 设计思想、协议、系统机制：优先论文、RFC、设计文档、release notes、源码或作者原文。
- 稳定经典概念：可参考经典解释文章。
- 快速变化主题：必须优先近期资料。

始终把用户给的原文作为主文本。外部资料只用于澄清、校正、补充类比或更新时效性。凡是外部资料影响了判断，要给出来源链接。

### 5. 带领读者分段阅读

按文本结构或项目结构分段推进。每一段都按这个节奏：

1. 说清这一段在回答什么局部问题。
2. 用 2-5 句话概括作者在这一段做了什么推进。
3. 对关键技术内容使用五个镜头解释。
4. 点出隐藏前提、容易误解处和需要补齐的背景。
5. 提 1-3 个问题，让读者先想一想再继续。

在检查点给读者选择，例如：

- 继续往下读。
- 放慢，讲透某个概念。
- 跳到实现或代码。
- 和另一个技术比较。
- 先整理成博客笔记。

如果读者没有选择，只说“继续”或类似表达，就按默认阅读路径推进。

### 6. 维护概念台账

阅读过程中维护一个简短的概念台账，避免讨论散成摘要：

- `概念`：术语、机制、接口或设计选择。
- `一句话定义`：精确说明它是什么。
- `为什么存在`：它解决的问题或张力。
- `前置概念`：读者需要先懂什么。
- `工作机制`：核心运行模型。
- `同构技术`：哪些技术共享类似设计原理。
- `迁移启发`：这个思想还能用到哪里。

必要时在每轮伴读后更新台账，而不是等到最后一次性补。

### 7. 推荐延伸阅读

如果阅读过程中发现更深的知识脉络，推荐少量延伸材料：

- 1-2 个官方、论文、RFC、源码或作者原文。
- 1-2 个经典解释材料。
- 如果主题变化很快，再给 1 个近期材料。

每个推荐都说明它回答什么问题、为什么值得读。不要堆长书单。

## 最终博客

阅读完成后，用中文产出一篇博客文章，除非用户明确要求其他语言。

博客必须做到：

- 以问题串联全文，而不是平铺总结。
- 融合原作者观点、读者在伴读中提出的问题或反应，以及 Codex 的分析。
- 形成连续链条：问题 -> 朴素直觉为什么不够 -> 关键概念 -> 工作机制 -> 相邻比较 -> 应用场景 -> 剩余问题。
- 技术表达准确，但不牺牲可读性。
- 必要时加入代码或伪代码，让机制落地。
- 明确写出可迁移的思想：这个技术不只教会读者怎么用，还教会读者怎样思考一类问题。

默认结构：

1. 开场问题：这个技术背后真正让人困惑的张力是什么？
2. 为什么会有这个问题：上下文、约束、旧方案和失败的直觉。
3. 核心概念是什么：定义、边界、承诺和非承诺。
4. 它如何工作：机制、例子、代码或伪代码、取舍。
5. 它像什么又不像什么：同构技术、相邻概念和常见误解。
6. 它能用在哪里：典型场景、失败边界和工程判断。
7. 它打开了什么思考：可迁移原则和仍值得追问的问题。

只有在延伸阅读确实能继续加深理解时，才在文末附简短阅读清单。
