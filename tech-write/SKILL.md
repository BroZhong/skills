# Tech Write

## 目标

写出真正帮助技术读者建立理解的文章，而不是把资料改写成摘要。文章必须回答一个清晰的技术问题：它为什么出现，旧直觉为什么不够，关键概念承诺什么，机制如何运转，工程上如何取舍，以及这套思想还能迁移到哪里。

默认写中文技术长文。风格参考《凤凰架构》：以问题为叙事主线，用历史压力和现实约束引出概念，用精确定义压住术语，用机制和例子证明判断，用温和但明确的工程立场收束全文。参考的是写作方法和气质，不复刻原文句子。

## 可接受输入

- 主题：如“写一篇 Raft 入门文章”“讲清楚服务发现”。
- 素材：技术文章、链接、本地文件、论文、项目目录、读书笔记、会议记录。
- 目标：面向新人、团队分享、公众号长文、架构决策说明、项目复盘、选型分析。
- 草稿：重写、扩写、改成更有脉络的技术文章。

如果素材来自文章、论文或项目，先用 `tech-read` 的思路建立阅读地图，再进入写作。来源不明确、事实可能过时、API 或版本行为会影响判断时，要检索官方文档、论文、RFC、release notes 或源码补足证据，并在文末列出必要来源。

## 工作流

### 1. 确定写作契约

先确认或自行推断四件事，不因细节缺失而停住：

- `读者`：新人、熟练工程师、架构师、团队决策者，还是非技术读者。
- `目的`：解释概念、说服选型、复盘事故、介绍项目、教学入门，还是形成判断。
- `深度`：`short` 快速成文，`normal` 完整长文，`deep` 加入历史、机制、比较、实践和延伸阅读。
- `语气`：默认理性、清晰、有作者判断；避免营销腔、百科腔和空泛鸡汤。

若用户没有指定，默认面向有基础的工程师，输出 `normal` 深度中文长文。

### 2. 找到核心张力

正式写作前，先在内部形成一个“主问题”。文章不是从名词开始，而是从张力开始：

- 这个技术试图解决什么现实困境？
- 朴素方案为什么在规模、可靠性、复杂度、协作或表达上失败？
- 这个概念真正改变的是机制、边界、职责、成本，还是思维方式？
- 它牺牲了什么，换来了什么？
- 如果不用它，系统会在哪些场景下变得难以维持？

开头要让读者意识到“这里确实有一个问题”。不要用“本文将介绍……”作为主要开场；优先用现象、矛盾、反常识判断、历史转折或工程困境引出。

### 3. 用五个镜头组织材料

对每个关键概念、技术方案或架构选择，都用 `why / what / how / relation / application` 过一遍：

- `why`：为什么需要它？历史背景、需求压力、旧方案边界是什么？
- `what`：它到底是什么？区分名称、接口、行为、约束、保证和非保证。
- `how`：它如何工作？用步骤、数据流、调用链、伪代码、配置、图示或最小代码例子说明机制。
- `relation`：它和哪些概念相邻、同构或容易混淆？与旧方案相比差异在哪里？
- `application`：它适合什么场景？失效边界在哪里？工程上如何选择？

写作时不必显式使用这五个标题，但文章内容必须覆盖这些判断。

### 4. 采用凤凰架构式叙事骨架

默认长文结构如下，可按主题调整：

1. `开场问题`：用一个具体而有分量的问题打开。
2. `为什么会走到这里`：历史脉络、需求压力、旧方案的好处与局限。
3. `概念澄清`：给出精确定义，拆掉常见误解，说明术语边界。
4. `机制展开`：按流程、角色、状态、数据结构或交互时序讲清内部工作方式。
5. `对比与权衡`：说明它像什么、不像什么；适合什么、不适合什么。
6. `工程落地`：给出实现要点、配置/代码示例、实践经验、排错方向或选型建议。
7. `更深一层`：总结可迁移的思想，留下值得继续追问的问题。

文章应以问题推进，而不是以资料堆叠推进。每个大段落都要回答一个局部问题，段落之间要能看出推理链条。

### 5. 写出技术准确性

必须讲清名词定义与使用范围，机制中的角色、状态、输入、输出和失败路径，以及同步/异步、强一致/最终一致、控制面/数据面、机制/策略、接口/实现等分界。也要写出适用场景、前置条件、代价和不可承诺之处。

如果有代码，代码要最小但真实；如果有伪代码，要标明它用于说明机制而非可直接运行。当事实、版本、API 行为、项目现状可能变化时，不凭记忆写结论，先查官方或一手资料。

### 6. 模仿气质，不模仿句子

参考《凤凰架构》的写作气质：先承认旧方案为何合理，再指出它在新约束下为何不够；多用“从某个角度来看”“在真实系统里”“这意味着”这类推理转接；允许作者立场存在，但立场要由机制和约束推出；可以适度使用设问、类比和反例，但类比只负责开门，不能替代定义；引用他人观点、论文、项目或标准时，明确来源。

避免这些写法：只列优缺点清单、不解释问题来源；把技术讲成产品宣传；把复杂概念全靠比喻带过；用“本质上就是”掩盖没有定义清楚的地方；为了风格故意拉长句子。

### 7. 成稿后自检

交付前确认：文章是否有贯穿始终的主问题；读者是否知道技术为何出现；核心概念是否定义清楚，机制是否讲到可复述；是否写出了取舍、失败边界和适用场景；示例、代码、图示是否服务于机制解释；有没有未经核实的时效性判断；结尾是否提炼出可迁移的工程思想。

## 输出格式

默认直接给成稿，不先给冗长提纲。若材料很大或用户要求共创，先给一个短提纲和主问题，经用户确认后再写。成稿可以包含标题、二级标题、代码块、表格、mermaid 图和简短参考资料。除非用户要求，不写摘要式 TL;DR；技术长文的价值在推理过程里。
